这篇内容不是黑话速记表。黑话的作用是把一段共同背景压缩成一个词，但压缩之后也更容易被滥用。每个词都按三个问题展开：它是什么意思、什么时候会这样说、哪里容易误解。

## 怎么读这篇词典

看到一个词时，先把它还原成具体动作或约束，再判断它是不是适合当前场景。同一个词在产品讨论、代码评审和线上故障里可能指向不同的问题；“听起来专业”本身不代表方案正确。

## A. 快速交付黑话 {#jargon-a}

### 1. MVP（Minimum Viable Product）

- **白话**：为了验证核心假设，先做出能够被真实使用的最小版本。
- **常见场景**：团队想知道用户是否需要某个功能，先保留一条完整主流程，而不是一次做完所有边角功能。
- **边界**：MVP 是验证范围，不是粗制滥造的借口；核心流程仍然需要达到可使用、可观察的程度。

### 2. POC（Proof of Concept）

- **白话**：用一个小实验证明某个技术方案在原则上可行。
- **常见场景**：先验证某个库能否处理目标数据量，或某个硬件接口能否完成一次关键调用。
- **边界**：POC 证明的是可行性，不等于已经具备可维护性、安全性和上线条件。

### 3. Prototype（原型）

- **白话**：用低成本的模型或界面，提前感受流程和交互是否合理。
- **常见场景**：在写正式前端之前，用线框图或假数据走一遍用户操作。
- **边界**：原型可以隐藏大量实现细节；不能因为界面能点击，就推断后端、性能和数据模型已经完成。

### 4. Vertical Slice（垂直切片）

- **白话**：从界面、业务逻辑到数据存储，沿着一条用户路径做出一小块端到端功能。
- **常见场景**：先让“创建一条记录”完整跑通，再扩展编辑、搜索和批量操作。
- **边界**：垂直切片追求可验证的完整链路，不是把每一层都只写一个空壳接口。

### 5. Ship It

- **白话**：先把当前足够好的版本交付出去，让真实反馈进入下一轮迭代。
- **常见场景**：功能已经满足当前目标，继续打磨只是在猜测用户会不会需要的细节。
- **边界**：它不表示跳过测试、发布检查和回滚方案；交付速度必须和风险相匹配。

### 6. Dogfooding（吃自己的狗粮）

- **白话**：团队自己持续使用正在开发的产品或工具。
- **常见场景**：开发团队用自己的内部系统提工单、部署服务，从日常使用中发现问题。
- **边界**：内部用户和外部用户的需求可能不同；自用反馈很有价值，但不能替代外部验证。

### 7. Time to Market（上市速度）

- **白话**：从想法或需求确定，到用户能够真正拿到功能之间所花的时间。
- **常见场景**：比较不同方案时，讨论哪一种能更快完成验证和交付。
- **边界**：缩短时间不等于一味减少工作；返工、事故和维护成本也应计入总时间。

### 8. Product-Market Fit（PMF，产品市场匹配）

- **白话**：产品解决的问题已经被一群目标用户持续认可，并形成稳定需求。
- **常见场景**：产品团队观察留存、复用和付费等信号，判断是否值得扩大投入。
- **边界**：一次爆发式使用或少量好评不能单独证明 PMF；需要可重复、可持续的证据。

## B. 需求与产品黑话 {#jargon-b}

### 1. User Story（用户故事）

- **白话**：用用户、目标和价值描述一个待解决的问题。
- **常见场景**：把“加一个导出按钮”改写成“作为研究者，我想导出数据，以便在本地分析”。
- **边界**：用户故事不是完整设计稿；它要说明价值和边界，具体实现仍需补充。

### 2. Acceptance Criteria（验收标准）

- **白话**：明确什么条件满足后，大家可以认为需求完成。
- **常见场景**：在开发前写清输入、输出、错误提示和权限限制，减少“做完但不能验收”的争议。
- **边界**：验收标准不能只写“体验要好”；它需要能够被观察、检查或复现。

### 3. P0 / P1

- **白话**：项目内部用来表示优先级或严重程度的等级。
- **常见场景**：P0 可能表示阻断上线的故障，P1 可能表示需要尽快处理但有临时绕过办法的问题。
- **边界**：不同团队的等级定义不一样；写清本项目的含义，比争论数字大小更重要。

### 4. Happy Path（理想路径）

- **白话**：输入正常、权限足够、依赖可用时，用户顺利完成目标的主流程。
- **常见场景**：先描述“用户成功登录并提交表单”的流程，再补充失败情况。
- **边界**：Happy Path 只是起点；上线前还要覆盖错误输入、超时、重复提交和权限不足等情况。

### 5. Edge Case（边界情况）

- **白话**：不常发生，但处在规则边缘、容易暴露缺陷的输入或状态。
- **常见场景**：空列表、最大长度、跨天时间、重复点击和网络中断。
- **边界**：边界情况不是“用户不会这样做”；只要输入可达，就要决定系统如何处理。

### 6. Scope Creep（范围蔓延）

- **白话**：需求在执行过程中不断增加，导致原计划失去边界。
- **常见场景**：原本只做导出 CSV，后来又加入筛选、权限、定时任务和多格式下载。
- **边界**：新增需求本身不一定错误；问题在于没有重新评估时间、风险和优先级。

### 7. Closed Loop（闭环）

- **白话**：从发现问题、采取行动，到获得结果反馈，形成可以重复运行的完整链路。
- **常见场景**：收集错误日志、修复问题、验证修复效果，再把结果反馈到监控和流程中。
- **边界**：做了一个动作不等于形成闭环；必须有结果信号和下一步处理方式。

### 8. North Star Metric（北极星指标）

- **白话**：用一个长期核心指标描述产品是否持续为用户创造价值。
- **常见场景**：团队用“每周完成的有效分析次数”来统一讨论功能取舍。
- **边界**：指标是方向性工具，不是唯一目标；不能为了好看而牺牲数据质量或用户体验。

## C. 代码质量黑话 {#jargon-c}

### 1. DRY（Don't Repeat Yourself）

- **白话**：同一条容易变化的知识不要在多个地方重复维护。
- **常见场景**：多个模块使用同一套权限规则时，避免复制几份会逐渐分叉的判断逻辑。
- **边界**：表面相似的代码未必共享同一条知识；过早抽象会制造更难理解的耦合。

### 2. KISS（Keep It Simple, Stupid）

- **白话**：在满足需求的前提下，优先选择别人容易理解和维护的方案。
- **常见场景**：一个简单条件判断就能解决的问题，不引入复杂框架或多层配置。
- **边界**：简单不是少写代码，而是减少不必要的概念；真正复杂的业务不能靠删掉细节来伪装简单。

### 3. YAGNI（You Aren't Gonna Need It）

- **白话**：没有当前需求和证据支持时，不要提前实现未来可能用到的功能。
- **常见场景**：先支持确定的一个数据源，不为尚未确认的十种数据源设计完整插件系统。
- **边界**：YAGNI 不等于拒绝设计；已经明确的扩展约束仍然应该保留清晰的边界。

### 4. Tech Debt（技术债）

- **白话**：为了更快交付而留下的实现妥协，未来会带来额外维护成本。
- **常见场景**：先用人工脚本完成一次迁移，并记录后续需要自动化和补测试的工作。
- **边界**：不是所有旧代码都是技术债；只有已经产生或很可能产生额外成本的妥协才值得标记。

### 5. Code Smell（代码坏味道）

- **白话**：代码出现了可能难以维护的迹象，但它本身还不一定是功能错误。
- **常见场景**：超长函数、重复条件、隐藏的全局状态或一个类承担太多职责。
- **边界**：坏味道是需要调查的信号，不是见到某种写法就必须机械重构的规则。

### 6. Refactor（重构）

- **白话**：在不改变外部行为的前提下，改善代码内部结构。
- **常见场景**：先用测试固定现有行为，再拆分函数、改名或调整模块边界。
- **边界**：如果同时改变业务行为，就不只是重构；需要分别说明功能变化和结构变化。

### 7. Boilerplate（样板代码）

- **白话**：大量重复、结构固定、业务含义较少的代码或配置。
- **常见场景**：每个接口都要写一套相同的参数校验、序列化和错误包装。
- **边界**：样板代码不一定应该删除；它有时明确展示了协议和边界，自动生成也需要可追踪。

### 8. LGTM（Looks Good To Me）

- **白话**：代码审查者认为当前改动看起来可以接受。
- **常见场景**：审查者已经检查了范围、逻辑和验证结果，在合并前留下简短结论。
- **边界**：LGTM 不是“证明没有问题”；审查意见应该说明检查了什么，验证缺口也要留下记录。

## D. 调试与排障黑话 {#jargon-d}

### 1. Minimal Reproduction（最小复现）

- **白话**：删掉无关代码后，仍能稳定触发问题的最小案例。
- **常见场景**：把完整服务缩减成几十行输入和一个调用，交给同事或库作者定位。
- **边界**：最小不等于随意删；必须保留触发问题所需的环境、输入和时序条件。

### 2. Rubber Duck Debugging（橡皮鸭调试）

- **白话**：把代码和自己的推理逐步讲给一个不会打断你的对象听。
- **常见场景**：逐行描述输入、状态和预期，常常在说出口时发现假设不成立。
- **边界**：它适合澄清思路，不能替代日志、测试、调试器和实际证据。

### 3. Git Bisect（二分定位）

- **白话**：在一段提交历史中不断二分，找出首次引入问题的提交。
- **常见场景**：当前版本失败，但最近几十次提交都没有明显线索。
- **边界**：需要一个稳定、可自动判断好坏的检查；如果环境或测试本身不稳定，结果也会不可靠。

### 4. Root Cause Analysis（根因分析）

- **白话**：追溯导致故障发生的条件和机制，而不只描述最后一个报错。
- **常见场景**：不仅修复超时，还查清连接池耗尽、重试策略和监控缺失之间的关系。
- **边界**：根因通常是一组条件，不一定只有一个“罪魁祸首”；分析结论需要证据支撑。

### 5. Regression（回归）

- **白话**：原来正常的行为因为新改动再次出错。
- **常见场景**：修复导入功能后，旧的导出流程开始失败，于是补充回归测试。
- **边界**：回归描述的是变化前后关系，不等于所有新出现的 bug 都是回归。

### 6. Stopgap / Quick Fix（止血修复）

- **白话**：先降低影响、恢复服务或阻止扩散的临时处理。
- **常见场景**：先关闭异常开关、回滚版本或增加限流，再安排完整修复。
- **边界**：止血动作必须记录后续责任和期限，否则临时方案会变成永久债务。

### 7. Observability（可观测性）

- **白话**：通过日志、指标和追踪等外部信号，推断系统内部发生了什么。
- **常见场景**：根据请求追踪、队列长度和错误率判断一次延迟是在哪一层产生的。
- **边界**：有很多日志不等于可观测；信号需要能回答具体问题，并带有足够上下文。

### 8. Flaky Test（不稳定测试）

- **白话**：同样的代码和输入，有时通过、有时失败的测试。
- **常见场景**：依赖时间、线程调度、网络或共享状态，导致测试偶发失败。
- **边界**：不能把失败简单重跑到通过；应找到不稳定来源，否则它会掩盖真正的回归。

## E. 工程日常黑话 {#jargon-e}

### 1. CRUD（Create, Read, Update, Delete）

- **白话**：围绕数据记录进行创建、查询、修改和删除的基本操作。
- **常见场景**：后台管理系统、配置服务和简单资源接口经常以 CRUD 为主要功能。
- **边界**：CRUD 只是操作分类，不代表业务真的简单；权限、状态转换和审计仍然需要单独建模。

### 2. Glue Code（胶水代码）

- **白话**：把多个库、服务或模块接起来，让它们能够协同工作的适配代码。
- **常见场景**：把第三方 API 的字段转换成内部对象，再接入现有队列和错误处理流程。
- **边界**：胶水代码少而关键；如果没有边界和测试，最容易把外部差异扩散到整个系统。

### 3. Scaffolding（脚手架）

- **白话**：快速生成项目目录、基础配置和重复结构的工具或模板。
- **常见场景**：创建新服务时自动生成构建文件、健康检查、测试入口和目录结构。
- **边界**：脚手架加快起步，不代表生成的默认代码适合所有业务；生成后仍需理解和删改。

### 4. Legacy System（遗留系统）

- **白话**：仍然承担真实业务，但技术、文档或维护方式已经落后的系统。
- **常见场景**：老系统没有完整测试，却承载着不能轻易中断的核心流程。
- **边界**：遗留不等于无价值；判断改造优先级时要看业务影响、风险和替代成本。

### 5. Compatibility Layer（兼容层）

- **白话**：位于新旧接口之间，负责转换差异并保持双方暂时能够协作的一层代码。
- **常见场景**：新服务使用新字段，但旧客户端仍依赖旧字段格式。
- **边界**：兼容层应有清晰的生命周期和删除条件，否则会长期隐藏真实接口差异。

### 6. Hotfix（热修复）

- **白话**：针对线上紧急问题，快速发布的修复版本。
- **常见场景**：支付失败或数据泄漏风险需要立即降低影响，不能等待完整迭代周期。
- **边界**：热修复仍需要最小验证、发布记录和回滚路径；紧急不代表可以失去控制。

### 7. Idempotency（幂等）

- **白话**：同一个请求执行一次或多次，最终结果保持一致。
- **常见场景**：网络重试时，支付、创建订单或提交任务不能因为重复请求产生多份结果。
- **边界**：幂等通常需要请求标识、状态记录或唯一约束；“接口返回成功”本身不等于幂等。

### 8. Backfill（数据回填）

- **白话**：根据新规则或新字段，为历史数据补齐缺失内容。
- **常见场景**：新增 `created_at` 字段后，为旧记录计算并写入时间值。
- **边界**：回填要考虑批量大小、可重复执行、错误恢复和对线上读写的影响。

## 记住这件事

黑话是压缩工具，不是判断工具。遇到一个词，最好继续追问三件事：具体对象是什么、当前证据是什么、做完之后如何验证。这样才能把“快速 MVP”“技术债”或“根因分析”从口号还原成可执行的工程动作。
